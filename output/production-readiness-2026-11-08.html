오핀(OhPin) 서비스 건강검진 보고서

검진일 2026-11-08 · 대상: 프론트엔드(Next.js), Next API, 백엔드(Spring), AWS EC2, Supabase · 운영 사이트 ohpin.newdawn.co.kr

이 보고서는 이렇게 읽어요. 오핀은 "선생님이 슬라이드를 보여주고, 학생들이 슬라이드 위에 PIN을 찍어 질문하는" 서비스예요. 이 서비스가 사는 집(서버)과 길(네트워크), 창고(데이터베이스)를 의사 선생님처럼 하나씩 진찰했어요. ✅ 건강 ⚠️ 주의 🚨 위험 세 가지 신호등으로 표시했어요.

1. 한 줄 결론

지금처럼 작은 규모(한 번에 수업 1~5개, 학생 수백 명)는 돌아갑니다. 하지만 "안심하고 운영할 수 있는 프로덕션" 기준에는 아직 못 미칩니다.

이유는 세 가지예요. ① 서버가 한 대뿐이고 그 서버가 숨 쉴 공간(메모리)이 거의 없어서, 큰 파일 변환 한 번에 전체가 멈출 수 있어요(11월 6일에 실제로 멈췄어요). ② 데이터 백업과 "아플 때 울리는 알람"이 하나도 없어요. ③ 무료 요금제(Supabase Free)라서 동시에 들어올 수 있는 학생 수가 약 200명에서 막혀요.

아래 "7장. 고치는 순서"의 빨간불 5개를 먼저 고치면 "작은 학교 한 곳 규모"는 안심하고 운영할 수 있고, 그 다음 단계(서버 분리·요금제 변경)를 하면 "학교 여러 곳" 규모로 갈 수 있어요.

쉽게 말하면: 지금은 손님이 아주 적은 가게예요. 하루에 Supabase 요청이 1,000건도 안 돼요. 그래서 "느리다"는 문제는 지금 없어요. 문제는 손님이 갑자기 늘면 어디서 먼저 막히느냐예요.

3. 서비스는 어떻게 생겼나요?

쉽게 말하면: 집(EC2)이 한 채인데, 그 집에 오핀 식구 둘(FE·BE)과 감시 카메라 5대, 심지어 다른 팀 식구들까지 같이 살아요. 집 전체 크기가 2 GB인데 평소에 1.4~1.6 GB를 이미 쓰고 있어요.

4. 부분별 진찰 결과

4-1. 프론트엔드 (브라우저 화면)

항목신호쉬운 설명과 근거
화면 응답 속도✅ 건강로그인 페이지 첫 바이트 70~90 ms, 참여 페이지 80~100 ms (3회 측정, 서울 Cloudflare 엣지 ICN). 매우 빠름.
화면 렌더 복잡도✅ 건강PIN 묶기(clusterPins), 질문 정렬, 폴더 집계가 10월 14일 감사에서 O(n²)→O(n log n)으로 정리됨.
첫 로그인 데이터 양⚠️ 주의첫 로그인 때 GET /instructor/courses가 그 선생님의 모든 강의·자료·슬라이드·질문을 한 번에 다 가져옴(p95 1.19초). 자료가 많아질수록 느려짐.
실시간 부하 설계✅ 건강학생은 30초마다만 확인, 질문 알림 후 0~10초 흩어서 재조회, 이모지 1초 1개 제한, 청중 수는 60초 심장박동. 서버를 아끼는 설계.
브라우저 보안 헤더⚠️ 주의FE 응답에 HSTS, X-Frame-Options, CSP가 없음(BE는 X-Frame DENY 있음). 다른 사이트가 오핀을 iframe에 넣을 수 있음.
자동 테스트⚠️ 주의테스트 파일 42개가 있지만 npm test 스크립트와 CI 테스트 단계가 없어 배포 전에 자동으로 돌지 않음(BE는 Gradle test가 배포 전에 돈다).

4-2. Next API (FE 서버가 직접 하는 일)

항목신호쉬운 설명과 근거
/api/rest/* 프록시⚠️ 주의모든 업무 API가 FE 서버를 지나 BE로 감. 지금은 BE를 공개 주소(Cloudflare 경유)로 부르므로 같은 집 안에서 길을 한 바퀴 돌아옴(요청마다 TLS 1회, nginx 1회 추가). 내부망 코드는 준비됐으나 BE 배포 실패로 아직 못 켬(4-3 참고).
/api/pdf 원본 PDF 전달⚠️ 주의학생 수 × PDF 크기만큼 EC2가 데이터를 직접 보냄. 디스크 캐시(3 GiB, 14일)와 512 KB 블록 공유로 Supabase 왕복은 줄였지만, 전송량 자체는 학생 수에 비례. t3.small 기준 대역폭 약 0.128 Gbps.
/api/pdf/page 페이지 이미지✅ 건강선생님 브라우저가 미리 그린 JPEG를 먼저 쓰고, 없을 때만 서버가 pdftoppm으로 그림(동시 2개 제한, PDFium은 메모리 1 GiB 여유 있을 때만 → 지금 서버에선 자동으로 꺼짐). 11월 7일 장애 뒤 안전하게 바뀜.
AI 요약·리포트✅ 건강Groq 호출 캐시 500건, 강사당 300회/시간 상한, 리포트 분석 1개씩 실행(oneRenderAtATime), 채팅 5회/리포트. 남용 방지선이 있음. 단, 캐시와 상한이 서버 메모리 안에 있어 서버가 2대가 되면 공유 저장소로 옮겨야 함.
매 요청 권한 확인✅ 건강PDF와 이미지 요청마다 요청자 토큰으로 Storage 메타데이터(RLS)를 다시 확인. 강의를 끄면 다음 요청부터 바로 막힘. 안전하지만 요청마다 Supabase 1회 호출이 붙음(p95 100~660 ms).

4-3. 백엔드 API (Spring, BE)

항목신호쉬운 설명과 근거
운영 중인 버전🚨 위험메모리 상한·내부망·변환 1개 제한을 넣은 BE 수정(PR #11, 11월 2일)이 배포에 실패해 운영 BE는 10월 15일 버전(05eadd8) 그대로. 실패 원인: GitHub 시크릿 ENV_FILE에 SPRING_PROFILES_ACTIVE 줄이 빠져 검증 단계에서 중단. 코드 문제가 아니라 설정 한 줄.
메모리 보호🚨 위험운영 BE는 mem_limit 없음, JVM 힙 최대 70%(약 1.4 GB), /tmp가 RAM 위(tmpfs 3 GB), PPT 변환 동시 2개. 2 GB 서버에서 변환 1건이면 넘침. 11월 6일 CPU 100%·응답 중단 장애의 배경.
요청마다 로그인 확인⚠️ 주의API 1건마다 Supabase /auth/v1/user(p95 566 ms)를 부르고 선생님이면 profiles(p95 375 ms)도 부름. 업무 처리 전 최대 0.9초가 먼저 들고, Supabase 호출이 API의 2~3배로 늘어남. JWT를 서버에서 직접 검증(JWKS)하거나 30초 캐시하면 해결.
PPT 변환⚠️ 주의슬롯이 차면 기다리지 않고 바로 "busy" 오류. 첫 이벤트를 다운로드·변환 뒤에 보내므로 큰 파일은 Cloudflare 100초 타임아웃(524)에 걸릴 수 있음. 작업 시작 직후 빈 이벤트 한 줄만 먼저 보내면 해결.
로그 양⚠️ 주의성공 요청까지 전부 INFO로 기록. 50 req/s면 하루 약 430만 줄이 메모리 256 MB Loki로 감. 느린·실패 요청만 남기도록 샘플링 필요.
CORS·헤더✅ 건강허용 오리진 명시, X-Frame DENY, 에러 메시지·스택 숨김, 컨테이너 read-only·cap_drop ALL. 잘 되어 있음.
HTTP 타임아웃✅ 건강Supabase 연결 10초, 요청 60초, 다운로드 15분. 가상 스레드 사용. 적절.

4-4. AWS 인프라 (EC2 한 대)

항목신호쉬운 설명과 근거
서버 크기⚠️ 주의t3.small(2 vCPU, 2 GB), 서울 2b. CPU는 14일 평균 약 11%로 여유. 메모리가 문제: 유휴 상태에서 가용 약 380~570 MB, 스왑 없음.
CPU 크레딧✅ 건강Unlimited 모드, 크레딧 잔고 576(최대), 14일간 초과 과금 0. 상태 점검 실패 0.
11월 5~6일 급등🚨 위험CPU 최대 99.8%·100.0%(다른 날은 13~43%). PDF 렌더와 변환이 겹쳐 메모리가 바닥나 스와핑처럼 멈춤(load 179). 재부팅으로 복구. 같은 조건이면 재발 가능.
백업🚨 위험루트 볼륨 스냅샷 0개. 디스크가 망가지면 서버 설정·캐시·모니터링 데이터 전부 복구 불가(앱 데이터는 Supabase에 있어 살아남음).
알람🚨 위험CloudWatch 알람 0개. 메모리·CPU·디스크가 차도 아무도 모름. 서버 안에 Grafana·Prometheus는 있지만 알림이 어디로 가는지 확인되지 않음.
방화벽(보안 그룹)⚠️ 주의80·443은 Cloudflare IP만 허용(좋음). 그러나 22(SSH)·3001·3306·3307이 전 세계(0.0.0.0/0)에 열림. 3306/3307은 듣는 프로세스 없음, 3001은 127.0.0.1 바인드라 지금 당장 노출은 없지만 닫아야 함. SSH는 내 IP 또는 Instance Connect 대역만.
관리 접근⚠️ 주의인스턴스에 IAM 역할이 없어 SSM 사용 불가. AWS CLI는 루트 계정으로 로그인 중(IAM 사용자·MFA 권장).
디스크⚠️ 주의gp3 30 GB, 60% 사용(10월 23일). FE는 옛 이미지를 지우게 고쳤고 BE도 고쳤지만 BE 쪽은 배포 실패로 미적용. 10월 23일엔 "디스크 꽉 참"으로 배포 실패한 적 있음.
배포 방식✅ 건강FE: 후보 컨테이너를 먼저 띄워 건강검사 → 통과하면 교체, 실패하면 자동 복구. 이전 컨테이너 1개 보존. 매우 좋음.
단일 장애점🚨 위험서버 한 대에 FE·BE·모니터링·다른 팀 서비스까지. 한 대가 멈추면 전부 멈춤. 가용 영역도 1곳.

4-5. Supabase 인프라 (로그인·DB·파일·실시간)

항목신호쉬운 설명과 근거
요금제🚨 위험Free(조직 ohpin). 무료 한도: 파일 1개 50 MiB(그래서 300 MB 자료 업로드가 413으로 실패), 파일 창고 1 GB, 실시간 동시 접속 약 200, 월 전송 5 GB, 자동 백업 없음, 7일 사용이 없으면 프로젝트 일시정지. 실제 운영에는 Pro가 필요.
DB 크기·건강✅ 건강Postgres 17.6, DB 24 MB, 접속 17/60. 최근 24시간 Postgres 오류 로그 0건. 가장 큰 테이블 questions 736 KB. 아주 여유.
파일 창고⚠️ 주의415 MB / 1 GB(41%), 1,488개. 자료가 1 GB까지 허용된 코드와 달리 창고 전체가 1 GB라 큰 자료 두세 개면 꽉 참.
LIVE 방치 강의🚨 위험강의 61개 중 35개가 LIVE 상태. 34개는 7일 이상(가장 오래된 것은 7월 22일부터), 선생님 19명 분. 서버에서 자동 종료하는 기능이 없고 브라우저 60분 타이머만 있어서 탭을 닫으면 영원히 LIVE. 그동안 "LIVE 강의면 참여자 열람 허용" 규칙(RLS·Storage 정책)이 계속 열려 있어, 코드만 알면 옛 자료와 질문을 볼 수 있음.
DB 인덱스⚠️ 주의외래키 인덱스 누락 13개(questions.slide_id, region_anchors.slide_id, materials.course_id 등). 같은 역할에 permissive 정책이 겹치는 테이블 9개. 지금은 데이터가 작아 안 느리지만 질문 수만 건부터 체감.
RLS 정책✅ 건강모든 공개 테이블에 RLS 켜짐. 정책 없는 6개 테이블은 서비스 역할 전용(의도). SECURITY DEFINER RPC 3개가 로그인 사용자에게 열려 있는데 리모컨·경험 설문용으로 의도된 것. 10월 25일 감사에서 교차 소유자 경로·질문 속도 제한(10/분, 100/강의) 등은 이미 막음.
익명 로그인 한도⚠️ 주의IP당 시간당 30회. 학교 Wi-Fi처럼 학생 수백 명이 IP 하나를 쓰면 31번째 학생부터 입장 실패. 대시보드에서 올려야 함.
Supabase 응답 속도✅ 건강최근 24시간 p95: lectures 282 ms, questions 112 ms, auth/user 566 ms, courses 1,193 ms. 오류 응답(4xx·5xx) 상위 25개 경로에 없음.

🚨 빨간불: 이번 주에 (돈 거의 안 듦, 대부분 설정)

  1. BE 배포 고치기. GitHub 시크릿 ENV_FILE에 SPRING_PROFILES_ACTIVE=prod 한 줄을 넣고 BE를 다시 배포. 그러면 메모리 상한 1 GB, 힙 40%, /tmp 디스크 이동, 변환 1개 제한, 내부망 연결이 한 번에 적용됨. 성공 뒤 FE ENV_FILE에 REST_API_URL=http://ohpin-be:8080을 넣고 FE 재배포(순서를 바꾸면 모든 API가 502).
  2. 스왑 2 GB 추가. 서버에서 fallocate로 스왑파일 하나. 메모리가 바닥나도 멈추지 않고 느려지기만 함. 11월 6일 같은 장애를 막는 가장 싼 보험.
  3. 알람 3개 걸기. CloudWatch: CPU 5분 평균 > 80%, 상태 점검 실패, 디스크 > 85%(에이전트 필요) — 또는 서버 안 Prometheus 알림 규칙에 컨테이너 메모리 85%·OOM 추가하고 알림이 실제로 Slack/메일로 가는지 한 번 확인.
  4. 백업 켜기. EC2 루트 볼륨에 Data Lifecycle Manager로 매일 스냅샷(7일 보관, 월 1~2달러). Supabase는 Pro로 가기 전까지 pg_dump를 주 1회 받아 두기.
  5. LIVE 방치 강의 정리 + 자동 종료. 지금 LIVE인 34개 옛 강의를 ended로 바꾸고(선생님 확인 후), DB에 pg_cron으로 "started_at 이후 N시간 지난 LIVE는 ended" 작업을 1시간마다 돌리기(또는 BE 스케줄러). 이게 없으면 "LIVE면 열람 허용" 규칙이 영원히 열려 있음.

⚠️ 노란불: 이번 달에

  1. Supabase Pro($25/월). 파일 50 MiB 한도 → 대시보드에서 1 GiB로 올림(300 MB 자료 업로드 문제 해결), 창고 100 GB, 실시간 500, 일 백업, 일시정지 없음. 익명 로그인 IP당 한도도 같은 화면에서 올리기(교실당 100명 이상).
  2. 방화벽 정리. 22는 내 IP와 EC2 Instance Connect 대역만, 3001·3306·3307 규칙 삭제. 인스턴스에 IAM 역할(SSM) 붙여서 SSH 포트 자체를 닫는 것이 목표. AWS 콘솔은 루트 대신 IAM 사용자 + MFA.
  3. BE 인증 캐시. Supabase JWT를 JWKS로 서버에서 직접 검증하고 profiles는 30초 캐시(BE 이슈 #9). API마다 0.5~0.9초 바닥 지연이 사라지고 Supabase 호출이 절반으로.
  4. DB 인덱스 13개 추가, 겹치는 정책 병합. 마이그레이션 한 개. 10분 작업.
  5. FE 보안 헤더. next.config.ts headers()에 HSTS, X-Frame-Options DENY(참여 페이지 포함), Referrer-Policy. 또는 Cloudflare Transform Rules.
  6. FE 테스트를 CI에. "test": "node --test" 스크립트와 deploy 워크플로 앞단에 lint·test 단계. BE는 이미 함.
  7. BE 변환 첫 이벤트 즉시 전송·로그 샘플링(이슈 #9). Cloudflare 100초 끊김과 Loki 과부하 예방.
